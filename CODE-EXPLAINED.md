the "what" — an examiner can read the code themselves, but they will ask why you
chose one approach over another.

## 1. How the three parts fit together

Three programs, each with one job:

```
  BROWSER                    BACKEND                   DATABASE
  React app       HTTP       Express API      SQL      MySQL
  port 5173     ────────>    port 5000     ────────>   port 3306
                <────────                  <────────
                  JSON                       rows
```

**The browser never touches MySQL.** It cannot — it has no database password.
It asks the backend, the backend decides whether that person is allowed, runs
the SQL, and sends back JSON.

This matters for security. If the browser could query the database directly,
anyone could open the developer console and read every password hash in your
users table. All the rules live on the server, where the user cannot edit them.

**One request end to end** — a cashier scans a barcode:

1. `Sell.jsx` calls `productApi.byBarcode('8850001000017')`
2. `client.js` attaches the JWT and sends `GET /api/products/barcode/8850001000017`
3. `product.routes.js` matches the URL, runs `authenticate` then the controller
4. `authenticate` verifies the token and loads the user
5. `product.controller.js` runs the `SELECT`
6. The row comes back as JSON, and the product appears in the cart

## 2. The database

**File: `database/schema.sql`**

Seven tables. Every table has `id` as its primary key and timestamps.

### roles
Three rows: `admin`, `cashier`, `customer`.

*Why a table instead of a text column on users?* Because a typo is then
impossible. `role = 'casher'` would be accepted by a text column and that user
would silently match no permission rule. A foreign key makes the database reject
it outright.

### users
Staff accounts. `password_hash` stores a bcrypt hash, never a password.

`is_active` is how staff are removed. Deleting a user would break the link to
the sales they rang up, so leavers are blocked instead. The foreign key from
`sales` is `ON DELETE RESTRICT`, so MySQL refuses to delete a user with sales
even if someone tries it by hand.

### categories
Product groupings. `ON DELETE SET NULL` on the product link: deleting a category
leaves the products alive with no category, rather than deleting your stock.

### products
`selling_price` and `cost_price` are `DECIMAL(10,2)`, **never `FLOAT`**. Floats
cannot represent 0.10 exactly, so money drifts by fractions of a cent and your
totals stop matching. `DECIMAL` stores exact values.

`stock_quantity` is the live figure the till reads. `low_stock_threshold` drives
the reorder warnings. `is_active` is the soft delete.

`sku` is generated by the app, not typed by staff. `barcode` is nullable because
loose goods do not have one.

### sales
One row per receipt. Stores the money breakdown, the payment method
(`cash`/`card`/`qr`), and `status` (`completed`/`voided`/`refunded`).

`invoice_no` is unique — no two receipts can share a number.

### sale_items
The lines on a receipt. **This is the most important design decision in the
schema:** `product_name`, `sku` and `unit_price` are *copies* taken at the time
of sale, not lookups.

*Why?* If you raise a product's price next month and the receipt read the price
live from `products`, every old receipt would silently change to the new price.
Your February revenue would rewrite itself in March. Snapshots make history
permanent.

### inventory_logs
An append-only record of every stock movement: what changed, by how much, what
it was before and after, who did it, and why.

Nothing ever updates or deletes a row here. When stock looks wrong, this table
tells you exactly which sale or adjustment caused it.

### v_low_stock
A view — a saved query that behaves like a table. It lists products at or below
their reorder level, so the dashboard does not repeat that logic.

## 3. Backend — foundations

### `src/server.js`
The starting point. Tests the database connection **before** starting the web
server, so a wrong password gives you a clear message immediately instead of
mysterious failures on the first request.

### `src/app.js`
Assembles Express and the order things run in. Order matters: CORS, then JSON
parsing, then logging, then static files, then routes, then error handling
last — the error handler must be last or errors will pass it by.

**CORS** decides which websites may call this API from a browser. In development
it allows any origin, because your laptop's wifi address changes. In production
only listed addresses are allowed.

### `src/config/env.js`
Reads `.env` and checks the required values are present. If `JWT_SECRET` is
missing it prints what is wrong and exits, rather than starting up and failing
later in a confusing way.

*Why `.env` at all?* So passwords are never in the code. The file is
git-ignored; `.env.example` is committed showing the shape without the secrets.

### `src/config/db.js`
Owns the connection to MySQL. Four exports:

- **`query(sql, params)`** — run SQL, get rows back.
- **`queryOne(sql, params)`** — the same, first row only.
- **`withTransaction(callback)`** — run several statements as one all-or-nothing
  unit. Commits if the callback finishes, rolls back if it throws.
- **`testConnection()`** — used at startup.

It uses a **connection pool**, not a single connection. Opening a database
connection is slow; a pool keeps ten open and hands them out as needed.

**Parameters are never glued into the SQL string.** `query('... WHERE id = ?',
[id])` sends the SQL and the value separately, so the value can never be read as
SQL. This is what prevents SQL injection, and it is a question you will be
asked.

### `src/config/upload.js`
Rules for product photos, using multer.

- Files go to `backend/uploads/products/`, not into the database. Storing images
  as BLOBs slows every query that touches the products table.
- **The uploaded filename is thrown away.** Each file gets a random name and the
  extension comes from the MIME type we already checked. A browser will happily
  send a file called `../../src/server.js`, and accepting that name is how
  people overwrite their own servers.
- JPG, PNG, WEBP, GIF only. 2 MB maximum.
- **`removeLocalImage(url)`** deletes a file when a photo is replaced, so the
  folder does not grow forever. It ignores external URLs and missing files —
  a failed cleanup should never break the request the user actually made.

### `src/utils/ApiError.js`
An error class carrying an HTTP status. `ApiError.notFound('Product not found')`
instead of a plain error, so the error handler knows to send 404 rather than
500.

### `src/utils/asyncHandler.js`
A three-line wrapper. Express 4 does not catch errors thrown inside `async`
functions — the request just hangs. This wraps each handler so rejections reach
the error middleware.

### `src/utils/helpers.js`
- **`money(n)`** — rounds to 2 decimals, avoiding float drift.
- **`toCSV(rows)`** — turns rows into CSV, quoting values containing commas or
  quotes. Written by hand rather than pulling in a library for twelve lines.
- **`paginate(qs)`** — safe page/limit values, capped at 100 so nobody can ask
  for a million rows.

### `src/utils/emvqr.js`
Builds the bank QR payload. Three functions:

- **`tlv(tag, value)`** — one block: a 2-digit tag, a 2-digit length, the value.
  That is the entire format.
- **`crc16(input)`** — CRC-16/CCITT-FALSE, the checksum EMVCo specifies. Verified
  against the standard check value: `crc16('123456789')` must equal `29B1`.
- **`buildPayload(cfg, amount, ref)`** — assembles the blocks in order and
  appends the checksum.

This is the standard behind KHQR/Bakong, PromptPay and QRIS. **The system does
not verify payment** — nothing contacts the bank. The cashier checks their
banking app and confirms.

## 4. Backend — middleware

Middleware are functions that run *before* a controller. Each either passes
control on with `next()` or stops the request.

### `src/middleware/auth.js`

**`authenticate`** — reads `Authorization: Bearer <token>`, verifies the
signature, then **re-loads the user from the database on every request**.

*Why re-load, when the token already holds the user?* Because if you block
someone, they must lose access immediately. A token is valid for 8 hours;
without this check a blocked cashier could keep selling until it expired.

**`authorize(...roles)`** — returns a middleware that checks the role.
`authorize('admin')` on a route means only admins reach the controller.

**These two are the actual security.** Hiding buttons in the frontend is
convenience; this is what stops a cashier calling the reports endpoint directly.

### `src/middleware/validate.js`
Collects failures from the express-validator rules and turns them into one 400
response listing each bad field.

### `src/middleware/errorHandler.js`
The single place errors become responses.

**`notFound`** — anything matching no route becomes a clear 404.

**`errorHandler`** — translates raw MySQL error codes into sentences a user can
act on. `ER_DUP_ENTRY` becomes "A record with that unique value already exists",
not a stack trace. Stack traces are logged for 500s in development only —
leaking one to a browser tells an attacker your file paths and library versions.

## 5. Backend — controllers

Controllers hold the actual work: read the request, run SQL, send JSON.

Every response uses the same envelope, so the frontend never has to guess:

```jsonc
{ "success": true,  "data": { ... }, "pagination": { ... } }
{ "success": false, "message": "Not enough stock for \"Cola Can\": 3 left" }
```

### `auth.controller.js`

**`signToken(user)`** — creates a JWT holding the user id, username and role,
signed with `JWT_SECRET` and expiring in 8 hours (about one shift).

*What is a JWT?* Three parts: what it claims, and a signature over that claim
made with your secret. Anyone can read it; nobody can change it without the
secret, because the signature would stop matching.

**`login`** — finds the user, compares the password with `bcrypt.compare`, and
returns a token.

Two details worth pointing out:
- **The same message for "no such user" and "wrong password."** Different
  messages let an attacker discover which usernames exist.
- **`bcrypt.compare`, not `===`.** The stored value is a hash. Hashing is
  one-way: you cannot turn a hash back into a password, you can only hash the
  attempt and see if it matches.

**`register`** — admin-only. Hashes the password with a cost of 10 (2^10
rounds), which makes brute-forcing a stolen database slow.

**`me`** — returns the current user; used by the frontend on refresh.

**`changePassword`** — verifies the current password before setting a new one.

**`listUsers`**, **`setUserStatus`** — the Staff screen. `setUserStatus` refuses
to let you block yourself, otherwise the last admin could lock everyone out.

### `product.controller.js`

**`generateSku(conn, categoryId)`** — builds a code from the category initials
plus a running number: `BEV-0001`, `SNK-0002`. Staff never invent codes, but
reports and receipts still have a stable identifier.

**`list`** — search, category filter, low-stock filter, pagination. Filters are
built into a `WHERE` array so only the ones actually used are added.

**`getByBarcode`** — the scanner path. Matches barcode *or* SKU so loose goods
can be found by their code.

**`create`** — inserts the product and, if it has opening stock, writes the
matching `inventory_logs` row. Both inside a transaction, so a product can never
exist without its opening-stock record.

**`update`** — deliberately **cannot change stock**. Editing a product changes
its name and prices; stock moves through `adjustStock` so every change has a
reason attached.

Note the image handling: `image_url` is set explicitly rather than with
`COALESCE`, because the user must be able to *clear* a photo. `COALESCE` would
read "no photo" as "leave it alone".

**`adjustStock`** — the audit-trail function. It:
1. locks the product row with `SELECT ... FOR UPDATE`
2. checks the result would not be negative
3. updates the stock
4. writes an `inventory_logs` row with before, after, who and why

All in one transaction. `quantityChange` is a **delta** (+24 received, −3
damaged), not a new total, because a delta records what happened rather than
just the result.

**`remove`** — sets `is_active = FALSE`. A real delete would orphan every sale
line referencing it.

**`lowStock`** — reads the `v_low_stock` view.

### `sale.controller.js` — the heart of the system

**`checkout`** is the function to present. Walk through it slowly:

**Step 1 — merge duplicates.** Scanning the same item twice produces two lines;
they are merged into one with quantity 2.

**Step 2 — sort by product id.** This prevents *deadlock*. If cashier A locks
product 5 then wants 9, while cashier B locks 9 then wants 5, both wait forever.
Locking in the same order every time makes that impossible.

**Step 3 — open a transaction.** Everything below either all happens or none of
it does.

**Step 4 — for each line, lock the product row** with `SELECT ... FOR UPDATE`.
This stops two cashiers selling the last unit at the same moment. The second one
waits until the first commits, then sees the updated stock.

**Step 5 — read the price from the database.** The cart only sends `productId`
and `quantity`. If someone edits the frontend to send `"price": 0.01`, it is
ignored. **This is the difference between a school project and something you
could run a till on.**

**Step 6 — check stock**, and fail with a readable message naming the product
and both numbers.

**Step 7 — insert the sale**, then rewrite `invoice_no` using the real
auto-increment id (`INV-20260825-00042`). Two steps, because the id does not
exist until after the insert, and counting today's sales to guess the next
number would produce duplicates under load.

**Step 8 — for each line:** insert the `sale_items` row with its price snapshot,
reduce the stock, write the `inventory_log`.

**Step 9 — commit.** If anything threw, `withTransaction` rolls everything back.

If the fourth item in a cart is short by one unit, the first three are *not*
deducted. Without the transaction you would get phantom stock loss and a sale
that half-exists.

**`getSaleWithItems(id)`** — loads a sale, its lines, and the shop details for
the receipt header.

**`list`** — filters by date, status, cashier. Note the role rule:

```js
if (req.user.role === 'cashier') { where.push('s.user_id = ?'); params.push(req.user.id); }
```

A cashier is *silently* restricted to their own sales, in the SQL. They cannot
ask for someone else's by changing a URL parameter.

**`voidSale`** — admin only. Puts every item back on the shelf, writes reversal
rows to `inventory_logs`, and marks the sale `voided`. The sale is never
deleted, so the receipt number stays accounted for. A missing invoice number in
a sequence is what auditors look for.

### `report.controller.js`

**`range(qs)`** — defaults to the last 30 days when no dates are given.

**`summary`** — the four dashboard cards: today, this month, stock value, and
low-stock counts.

**`revenue`** — groups sales by day, week or month using `DATE_FORMAT`, and
returns data **already shaped for Chart.js** (`labels` and `datasets`) so the
frontend just hands it over.

**`topProducts`** — sums quantities from `sale_items`. Note it groups by the
*snapshot* name, so a renamed product still reports correctly for past sales.

**`byCategory`**, **`paymentMethods`**, **`stockLevels`** — the other charts.

**`fetchExportRows(type, from, to)`** — one place that decides what goes into an
export, used by both CSV and PDF so they can never disagree.

**`exportReport`** — sets `Content-Disposition: attachment` so the browser
downloads rather than displays, then either sends CSV text or streams a PDF
built with PDFKit.

### `payment.controller.js`
**`paymentQr`** — returns either a generated EMVCo payload with the amount in
it, or the URL of a saved bank QR image, depending on `.env`. The saved image
always wins: a real code from the bank is more trustworthy than one we built.

### `upload.controller.js`
**`productImage`** — returns the stored path after multer has saved the file.
**`removeProductImage`** — deletes a file.

Uploads are a separate endpoint from product create/update so the product
endpoints stay plain JSON. The frontend uploads first, then sends the path.

### `public.controller.js`
The customer-facing endpoints — the only ones with no login.

**`products`** deliberately does **not** return `cost_price` or exact stock
counts. It returns an availability word: `in_stock`, `low`, `out_of_stock`. A
shopper has no business knowing your margins, and the safest way to keep data
private is to never send it.

### `category.controller.js`
CRUD plus one rule: **`remove`** refuses to delete a category that still has
products, and says how many. Better than either silently deleting stock or
showing a raw foreign-key error.

### `inventory.controller.js`
**`logs`** — the audit trail with filters, joined to product and user names.

## 6. Backend — validators and routes

### Validators (`src/validators/`)
Rules describing what a valid request looks like. `product.validator.js` says
`sellingPrice` must be a number ≥ 0, `name` must be 2–150 characters.

*Why validate on the server when the form already checks?* Because the form can
be bypassed. Anyone can send a request with Postman. **Frontend validation is a
convenience for honest users; backend validation is the actual rule.**

### Routes (`src/routes/`)
Routes map a URL to a chain of middleware ending in a controller. Read one:

```js
router.post('/', authorize('admin'), v.create, validate, ctrl.create);
```

Left to right: must be an admin → check the fields → convert failures to a 400 →
run the controller. Each step can stop the request.

`routes/index.js` mounts every group under `/api`, and adds `/api/health` for
checking the server is alive.

The permission map, visible in the route files:

| Route group | Who |
|---|---|
| `/public/*` | anyone, no token |
| `/products` (read) | admin + cashier |
| `/products` (write) | admin |
| `/products/:id/stock` | admin + cashier |
| `/sales` | admin + cashier (cashier sees own) |
| `/sales/:id/void` | admin |
| `/reports/*`, `/inventory/*`, `/uploads/*` | admin |
| `/payments/qr` | admin + cashier |

## 7. Frontend — foundations

### `main.jsx`
Mounts React onto the page. Three lines.

### `App.jsx`
The router. Public routes (`/login`, `/shop`, `/display`) sit outside the
layout; admin and cashier routes are wrapped in `ProtectedRoute` and `Layout`.

**`RoleHome`** sends a signed-in user to the right home screen and a stranger to
the shop.

### `api/base.js`
**`resolveApiBase()`** works out where the backend is.

The problem it solves: `localhost` means "this device". That is right on your
laptop, but when a tablet opens the app over wifi, `localhost` means the
*tablet*, which has no backend on it. So when the page is served over the
network, this points the API at the same host the page came from.

### `api/client.js`
One configured axios instance, with two interceptors:

- **Request** — attaches the JWT to every call, so no component has to remember.
- **Response** — turns the backend's error envelope into a plain message, and
  if a 401 comes back, clears the token and redirects to login.

Being able to say "authentication is handled in one file" is a good answer to
"how do you avoid repeating yourself".

### `api/endpoints.js`
One function per endpoint, grouped by area: `productApi.list()`,
`saleApi.checkout()`. Components never write URLs, so changing an endpoint means
editing one line here rather than hunting through pages.

### `context/AuthContext.jsx`
Holds the signed-in user for the whole app.

**`AuthProvider`** — on page load, if a token exists it calls `/auth/me` to ask
the server who it belongs to, rather than trusting anything cached.

**`login()`**, **`logout()`**, **`useAuth()`** — the hook any component uses to
read the current user.

### `utils/format.js`
`money()`, `number()`, `dateTime()`, `daysAgo()`. All formatting lives here so
prices look identical everywhere.

### `utils/image.js`
**`imageSrc(path)`** — turns a stored relative path into a full URL. Paths are
stored relative so moving the backend to a real domain needs no data changes.

### `utils/customerDisplay.js`
Syncs the customer-facing screen using **BroadcastChannel**, which passes
messages between windows of the same browser.

**`publishCart()`**, **`publishSale()`**, **`subscribe()`**,
**`openCustomerDisplay()`**.

*Why not websockets?* This needs no server, no extra library, no reconnection
logic. The honest limitation: same computer, same browser. A tablet across the
counter would need the backend to relay the cart.

## 8. Frontend — shared components

### `components/ProtectedRoute.jsx`
Redirects to login if there is no user, or home if the role is wrong.

**Say this out loud in your presentation:** this is convenience, not security.
The backend re-checks on every request. Hiding a page does not protect the data
behind it.

### `components/Layout.jsx`
The frame around every signed-in screen. Sidebar on desktop, **bottom bar on
tablet** — a cashier holding a tablet reaches the bottom with their thumb, not
the top-left corner. The nav list is built from the user's role.

`deskOnly: true` keeps Staff out of the tablet bar; managing staff is desk work.

### `components/ui/` — the building blocks
`Button`, `Field`/`Input`/`Select`/`Textarea`, `Modal`, `Toast`, `Feedback`
(`Spinner`, `ErrorNote`, `EmptyState`, `Badge`), `Thumb`, `ImageUpload`.

Built once, used everywhere: one place to change how every button looks, and
every error looks the same so users learn the pattern once.

**`ImageUpload`** uploads the moment a file is picked rather than on save, so
the preview is the real file on the server, not a local illusion that might fail
later. `capture="environment"` opens the camera on phones.

**`Modal`** closes on Escape and locks background scrolling.

### `components/charts/`
**`registerCharts.js`** — Chart.js v4 is modular; you must register the pieces
you use once before any chart renders.

**`Charts.jsx`** — `RevenueChart` (line), `TopProductsChart` (horizontal bar, so
product names have room), `CategoryChart` (doughnut), `StockChart` (grouped bar
comparing stock against reorder level). Each shows a friendly message when there
is no data.

### `components/Receipt.jsx`
The printable receipt. The `@media print` rules in `index.css` hide everything
except `#receipt`, so Ctrl+P produces a receipt sized for a 76mm thermal roll,
not a screenshot of the app.

### `components/PaymentQr.jsx`
Fetches the payload and draws it to a canvas with the `qrcode` library, or shows
the saved bank image. Prints the amount underneath and reminds the cashier to
confirm the money arrived first.

## 9. Frontend — pages

### `pages/Login.jsx`
Username and password, error display, redirect by role.

### `pages/admin/Dashboard.jsx`
Loads six endpoints in parallel with `Promise.all` — six sequential requests
would take six times as long. Range switching (7 days to 12 months) re-runs the
effect. `Stat` and `Panel` are small local components so the markup stays
readable.

### `pages/admin/Products.jsx`
The product list. Search is **debounced** by 350ms so typing "water" fires one
request instead of five. Table on desktop, cards on mobile. Opens
`ProductFormModal`, `StockModal` and `CategoriesModal`.

### `pages/admin/ProductFormModal.jsx`
Add and edit in one component, since the fields are the same. Client-side
validation mirrors the server's rules so mistakes surface instantly. Shows live
profit per unit as you type the two prices. In edit mode it tells you stock is
changed elsewhere and why.

### `pages/admin/StockModal.jsx`
Delivery / return / correction, with a live preview of the result
(`42 → 66`) and a block on going negative.

### `pages/admin/Staff.jsx` and `StaffFormModal.jsx`
The staff list with role and status, and the add form. The block button does not
render on your own row.

### `pages/admin/Reports.jsx`
Date presets plus a manual range, sales and inventory tabs, and CSV/PDF export.

**Note `reportApi.download`:** a plain `<a href>` would not carry the
Authorization header and every export would fail with 401. It fetches the file
as a blob through the same axios client, then hands the browser a local URL.

### `pages/SalesHistory.jsx`
**One component serving both roles**, because the backend already scopes a
cashier to their own rows. The only difference is which columns show and whether
the void button appears.

### `pages/cashier/Sell.jsx` — the biggest screen

- **Scanning** — the barcode box holds focus; Enter looks the product up.
- **`addToCart`** — refuses out-of-stock items and will not exceed available
  stock.
- **`totals`** — a `useMemo` recalculating subtotal, discount, total and change
  whenever anything changes. Percentages are converted to an amount here,
  because the backend only stores money — storing "10%" would make old receipts
  change meaning if the rule were edited.
- **Payment** — cash (with change and an "Exact" button), card, or QR.
- **`handleCheckout`** — sends only ids and quantities, never prices.
- **Layout** — cart fixed beside the catalogue on desktop; a sheet behind a
  floating total button on tablet.

### `pages/CustomerDisplay.jsx`
The customer-facing screen. Large type, high contrast, **no controls** — nobody
should be able to change a sale from the customer's side of the counter. Shows a
thank-you with change due when a sale finishes.

### `pages/customer/Shop.jsx`
The public catalogue. Photo, name, price and an availability badge. No stock
numbers, no cost prices.

### `pages/cashier/CashierProducts.jsx`
Read-only catalogue plus the one write a cashier is allowed: correcting a stock
count.

## 10. The five things worth presenting

If you only have ten minutes, show these.

**1. The checkout transaction** (`sale.controller.js`). Row locks, all-or-nothing
writes, deadlock avoidance by lock ordering. This is the most technically
substantial thing in the project.

**2. Prices come from the database, not the request.** Show the cart payload —
just ids and quantities — and explain what a tampered client would achieve.
Nothing.

**3. The audit trail.** Every stock change has a before, an after, a person and
a reason. Demonstrate by making a sale and showing the matching log row.

**4. Snapshots in `sale_items`.** Change a product's price after a sale and show
the old receipt is unchanged.

**5. Role enforcement on the server.** Log in as a cashier in Postman, call a
reports endpoint, get 403. Then explain why hiding the button would not have
been enough.

## 11. Questions you will be asked

**"Why no ORM?"**
Every SQL statement is visible, which matters for a project we have to explain
and defend. An ORM would hide the transaction and locking behaviour that is the
most interesting part.

**"How do you prevent SQL injection?"**
Parameterised queries everywhere — `?` placeholders with values passed
separately, so a value can never be parsed as SQL. No string concatenation
anywhere in the codebase.

**"How are passwords stored?"**
bcrypt hashes with a cost factor of 10. Hashing is one-way. Even with the
database, an attacker cannot read the passwords, and each guess is deliberately
slow.

**"What if two cashiers sell the last item at the same time?"**
`SELECT ... FOR UPDATE` locks the row. The second waits for the first to commit,
then sees the updated stock and gets a clear "not enough stock" message.

**"What happens if the server crashes mid-sale?"**
The transaction was never committed, so MySQL rolls it back. No stock is
deducted and no partial sale exists.

**"Can a cashier see other cashiers' sales?"**
No. The filter is added in the SQL based on the token's user id. Changing a URL
parameter achieves nothing.

**"Why not delete products and users?"**
Both are referenced by sales history. Deleting either would orphan or destroy
records. They are deactivated instead, and the foreign keys enforce it.

**"Is the QR payment verified?"**
No, and say so plainly. Nothing contacts the bank. The cashier confirms the
payment arrived in their banking app before recording the sale. Real
verification needs a merchant API agreement, which is outside the project's
scope.

**"What would you do next?"**
Honest answers: refresh tokens instead of 8-hour ones; a password reset for
cashiers; barcode-label printing; a proper backup routine; and moving the
customer display onto the backend so it works across devices.

**"What was the hardest part?"**
Getting the checkout transaction right. The first version deducted stock outside
the transaction, which meant a failed sale could still reduce stock. Testing two
simultaneous checkouts is what surfaced it.
